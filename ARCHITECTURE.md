# Architecture — Flash Sale Inventory

## 1. Architecture and database locking strategy

The system uses a React + Vite dashboard and a Go/Gin REST API. PostgreSQL is the source of truth for inventory and reservation state. The frontend never calculates or mutates authoritative stock; it displays the backend response and refreshes periodically.

`inventory` stores `total_stock` and `reserved_stock`, with database checks preventing negative values and reserved stock from exceeding total stock. Available stock is derived as `total_stock - reserved_stock`, avoiding a separately stored value that could drift. `reservations` records owner, item, quantity, lifecycle status, expiry time, and confirmation time. A partial index supports scanning active reservations by item and expiry. A unique partial index on `idempotency_key` prevents duplicate reservation records for the same non-null key.

Reserve and confirm operations use explicit PostgreSQL transactions and lock the inventory row with `SELECT ... FOR UPDATE`. The inventory row is the serialization point for state changes on a given item. Reserve also uses a conditional `UPDATE` requiring `total_stock - reserved_stock >= quantity`; the check and increment occur atomically. Reservation creation and stock allocation commit together. Confirmation changes an active, unexpired reservation to confirmed and decrements both total and reserved stock in the same transaction. If any operation fails, the transaction rolls back.

Expired reservations are marked expired and their reserved quantities released in a transaction while the inventory row is locked. A periodic worker performs cleanup, while reserve/confirm also clean expired reservations for the relevant item so correctness does not depend on worker scheduling. The implementation uses a consistent inventory-first locking order in mutating flows to reduce deadlock risk. API handlers apply request context timeouts; the HTTP server handles SIGINT/SIGTERM and performs graceful shutdown.

## 2. Distributed scaling and failure modes

With ten stateless API instances, PostgreSQL locking remains effective across instances because the coordination occurs in the shared database, not in process-local mutexes. The main scaling constraints become connection multiplication, row contention for hot products, transaction duration, and expiry-worker contention. A pool of 20 connections per instance can mean up to 200 API connections before administrative or worker connections, so pool limits must be calculated against PostgreSQL capacity and adjusted with load testing. The expiry worker is safe to run in each instance because the inventory row lock serializes cleanup for the same item; a dedicated worker or advisory-lock/lease strategy could reduce duplicate scans.

For a larger deployment, keep API instances stateless behind a load balancer, use managed PostgreSQL with monitoring and carefully sized pools (or a pooler such as PgBouncer), tune indexes and transaction scope, and consider partitioning or queueing non-critical downstream work. A hot SKU remains serialized by design: correctness takes precedence over parallel writes to the same stock row. If requirements outgrow a single primary, redesign around partitioned inventory ownership or a dedicated reservation service rather than relying on application mutexes.

Failure cases include PostgreSQL unavailability, timeout while waiting on a row lock, client disconnects, and ambiguous commit results. The reservation API implements idempotency keys backed by a PostgreSQL unique partial index. Repeated requests with the same key and payload return the existing reservation, while reuse of the key with a different payload returns a conflict. Ambiguous commit outcomes can be retried with the same key to avoid creating a second reservation. Expiry is eventually cleaned by the worker, while reserve/confirm paths perform per-item cleanup to prevent expired holds from consuming stock indefinitely. Payment and other external side effects should not occur inside a database transaction; use an outbox/saga if such integrations are introduced.

## 3. Engineering trade-offs and AI transparency

Within the 4–8 hour limit, the implementation prioritizes database correctness, clear endpoint behavior, Docker reproducibility, and a functional operator dashboard. The dashboard polls every five seconds rather than using WebSockets, reducing implementation complexity at the cost of update immediacy. Reservation idempotency is implemented and covered by automated tests, including retries with the same key and payload and conflicts when a key is reused with a different payload. Authentication, metrics/tracing, and broader production-scale stress testing remain follow-up work rather than being represented as completed.

AI tools may help draft scaffolding or review edge cases, but generated code must be checked against the concurrency invariants and tested. One example of a flawed suggestion to watch for is using a Go `sync.Mutex` to protect stock: that only coordinates goroutines inside one process and cannot protect multiple service instances. The correction is to make PostgreSQL transactions and row-level locking authoritative.
